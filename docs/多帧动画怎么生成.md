# 怎么生成「连贯的多帧动画」

> 这份是研究结论 + 落地实现说明。结论先说：**不要一张一张生成图，要先生成视频再抽帧。**

---

## 一、为什么逐帧生图做不到连贯

让模型"生成第 1 帧、第 2 帧、第 3 帧……"的失败是**结构性的**，不是参数没调好：

| 问题 | 原因 |
|---|---|
| 角色会漂 | 每帧都是**独立采样**，没有任何机制把"第 2 帧"约束到"第 1 帧"附近 |
| 光照/色调会变 | 同上，每次采样都会重新决定一次色温 |
| 比例会跳 | 模型对"同一个角色"没有持久表示 |
| 动作不连续 | 模型不知道"上一帧手臂在哪"，它只知道你提示词里写了什么 |

**加 seed、加参考图、加 "same character" 都只是缓解**：seed 只锁初始噪声，参考图只锁外观不锁姿势与时间。

## 二、正确路线：视频 → 抽帧

视频模型不一样 —— **时间连贯性是它训练目标的一部分**。相邻帧在隐空间里必须靠近，否则视频会闪。所以"连贯"这件事是视频模型**白送你**的。

```
① 角色参考图（锁外观）
② 视频模型生成一段动画 ← 连贯性在这里被保证
③ 按目标帧率抽帧
④ 抠底 → 透明 alpha
⑤ 所有帧用**同一个包围盒**对齐 → 打包成精灵表
⑥ 出 精灵表 PNG + 描述 JSON
```

这也是这个圈子的主流做法，多个来源一致：

- **SpriteMaster / AutoSprite / FrameSprite** —— 一堆产品化的"AI video → sprite sheet"工具
- **video2sprites**（GitHub 教程）—— "extract the frames of a video for processing, and combining to create a sprite sheet with a transparent background"
- **sorceress.games** 的 2026 工作流文档 —— "generate the animation clip in AI Video Gen → turn video into frames at the true FPS"
- **ComfyUI 官方 sprite-sheet-generator 工作流** —— 三条工作流，全部是"图片 → 动画帧"
- **scenario.com** —— "combines image generation and video generation to produce animation-ready frame sequences"
- **r/aigamedev** 的讨论 —— "from the output video, extract the number of frames you need for your sprite sheet"

### 为什么连视频模型而不是"图生图链"

图生图链（frame N 用 frame N−1 当参考 + 低 denoise）也能动，但会**累积漂移**：每步误差都被下一帧继承，5~8 帧后角色已经不是原来那个了。视频模型是在整段序列上联合去噪，没有这个累积问题。

### 补充路线（当视频模型不好用）

| 路线 | 适用 | 代价 |
|---|---|---|
| **首尾帧 keyframe** 插值 | 只需要"从 A 姿势到 B 姿势"的过渡 | 需要模型支持 keyframe（我们的 `video` 工具支持） |
| **ComfyUI + AnimateDiff**（本地） | 有 GPU、想完全可控 | 要装权重、调 controlnet，学习曲线陡 |
| **逐件生成 + 骨架驱动**（我们之前做的 rig） | 需要精确控制关节 | **前提是部件能分开** —— 实测 AI 画不出可拆的部件，这条路上游就断了 |
| **手工/程序动画**（我们做的 procedural） | 占位、道具、几何体 | 美术上限低 |

## 三、落地实现：`spritesheet` 工具

```jsonc
// 1) 先确认 ffmpeg 和视频信息
spritesheet(action="info", video="D:\\动画\\walk.mp4")

// 2) 一条龙：视频 → 抽帧 → 抠底 → 对齐 → 精灵表 + JSON
spritesheet(action="from-video", video="D:\\动画\\walk.mp4",
            count=8, columns=4, scale=2, name="walk", loop=true)

// 3) 已经有 PNG 帧：直接打包
spritesheet(action="from-frames", frames=["D:\\f1.png","D:\\f2.png"], fps=12)

// 4) 把骨架动画烘成精灵表
spritesheet(action="from-rig", rig_config={project:"demo", name:"soldier"}, animation="walk_td", count=8)
```

产物：`<输出目录>/<项目>/anim/<名字>/` 下是 `<名字>_sheet.png` + `<名字>.json`

### JSON 格式（引擎无关，谁都能吃）

```jsonc
{
  "version": 1, "name": "walk", "image": "walk_sheet.png",
  "imageSize": [1232, 352],
  "cell": { "x": 0, "y": 0, "w": 308, "h": 176 },
  "grid": { "columns": 4, "rows": 2, "count": 8 },
  "fps": 4, "frameDurationMs": 250, "loop": true, "scale": 2,
  "pivot": [0.5, 1],          // 每格内的锚点：默认底边中点（站立角色贴地）
  "frames": [ { "index":0, "col":0, "row":0, "x":0, "y":0, "w":308, "h":176 }, … ]
}
```

运行时：按 `frames[i]` 从 `image` 里取格，按顺序播，间隔 `frameDurationMs`。

## 四、几个**必须做对**的细节（都是踩过的）

### 1. ★ 所有帧必须用**同一个包围盒**（防抖动）

逐帧各自紧裁再居中，会让角色每帧位置微微不同 —— 播起来就是**抖动**。这是 AI 视频转精灵表最常见的翻车点。

正确做法：先算所有帧的 **union 包围盒**，再统一裁。测试里专门有一条：
"三帧色块从左往右移动，打包后三格里的色块中心必须递增" —— 如果各自居中，三个中心会一样（看起来原地踏步）。

### 2. 抠底必须**从边缘泛洪**，不能全图颜色匹配

全图匹配会把角色身上与背景同色的区域一起抠掉（白底上的白牙、黑底上的黑靴都会变成洞）。
从边缘泛洪只吃"和外面连在一起"的那一片，角色内部的同色区安全。测试里有一条专测这个。

另外：边缘颜色不统一时（渐变、实景背景）**要拒绝抠** —— 硬抠会挖出奇怪的洞，不如老实告诉用户需要分割模型。

### 3. 循环动画要丢掉与首帧重复的末帧

视频循环的最后一帧往往和第一帧几乎一样。不丢的话，播放器会在末尾多停一帧，看起来"卡一下"。

### 4. 帧率不要照搬视频原帧率

游戏 sprite 通常 **8~12 帧**就够。一段 3 秒 30fps 的视频有 90 帧，全抽出来只是让文件变大 10 倍，视觉上看不出区别。
所以 `count`（"我要 8 帧"）比 `fps` 更直观 —— 插件内部用 `count / duration` 换算。

### 5. ffmpeg 找不到要**明确报错 + 给安装指引**

JavaScript 里没有靠谱的 mp4 解码器，这一步必须靠 ffmpeg。
所以 `findFfmpeg` 的查找顺序是：参数 → 环境变量 → PATH → 常见位置 → **按层浅扫**（BFS）。
找不到时返回 `howToFix` 数组，而不是静默失败或抛一个看不懂的错误。

> 顺便说：这台机器上 ffmpeg 就躺在剪映和 ComfyUI 的目录里，用户根本不知道有。
> 所以浅扫值得做 —— 但**必须按层**（BFS），深度优先会一头扎进某个子树把配额烧光（实测没找到）。

## 五、和之前「拆件骨架」路线的关系

两条路都留着，适用场景不同：

| | 视频抽帧 | 拆件骨架（rig） |
|---|---|---|
| 连贯性 | ✅ 视频模型保证 | ✅ 程序保证（数学上必然连贯） |
| 美术上限 | ✅ 高（模型画的） | ❌ 取决于分件质量 |
| 能否改动作 | ❌ 只能重新生成 | ✅ 改关键帧即可 |
| 上游风险 | 视频模型要能生成横向动作 | **AI 画不出可拆的部件**（实测：拆不开） |
| 适合 | 主要角色、复杂动作 | 数量大、需要变体、动作要复用 |

**放弃的是"让 AI 直接画出可拆部件"这个假设**，不是放弃 rig 本身 —— rig 仍然适合程序生成的素材（几何道具、我们那套俯视士兵）。
