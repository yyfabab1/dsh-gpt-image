# 怎么生成「连贯的多帧动画」

> 这份是研究结论 + 落地实现说明。结论先说：**不要一张一张生成图，要先生成视频再抽帧。**

---

## 一、为什么逐帧生图做不到连贯

让模型"生成第 1 帧、第 2 帧、第 3 帧……"的失败是**结构性的**，不是参数没调好：

| 问题 | 原因 |
|---|---|
| 角色会漂 | 每帧都是**独立采样**，没有任何机制把"第 2 帧"约束到"第 1 帧"附近 |
| 光照/色调会变 | 同上，每次采样都会重新决定一次色温 |
| 比例会跳 | 模型对"同一个角色"没有持久表示 |
| 动作不连续 | 模型不知道"上一帧手臂在哪"，它只知道你提示词里写了什么 |

**加 seed、加参考图、加 "same character" 都只是缓解**：seed 只锁初始噪声，参考图只锁外观不锁姿势与时间。

## 二、正确路线：视频 → 抽帧

视频模型不一样 —— **时间连贯性是它训练目标的一部分**。相邻帧在隐空间里必须靠近，否则视频会闪。所以"连贯"这件事是视频模型**白送你**的。

```
① 角色参考图（锁外观）
② 视频模型生成一段动画 ← 连贯性在这里被保证
③ 按目标帧率抽帧
④ 抠底 → 透明 alpha
⑤ 所有帧用**同一个包围盒**对齐 → 打包成精灵表
⑥ 出 精灵表 PNG + 描述 JSON
```

这也是这个圈子的主流做法，多个来源一致：

- **SpriteMaster / AutoSprite / FrameSprite** —— 一堆产品化的"AI video → sprite sheet"工具
- **video2sprites**（GitHub 教程）—— "extract the frames of a video for processing, and combining to create a sprite sheet with a transparent background"
- **sorceress.games** 的 2026 工作流文档 —— "generate the animation clip in AI Video Gen → turn video into frames at the true FPS"
- **ComfyUI 官方 sprite-sheet-generator 工作流** —— 三条工作流，全部是"图片 → 动画帧"
- **scenario.com** —— "combines image generation and video generation to produce animation-ready frame sequences"
- **r/aigamedev** 的讨论 —— "from the output video, extract the number of frames you need for your sprite sheet"

### 为什么连视频模型而不是"图生图链"

图生图链（frame N 用 frame N−1 当参考 + 低 denoise）也能动，但会**累积漂移**：每步误差都被下一帧继承，5~8 帧后角色已经不是原来那个了。视频模型是在整段序列上联合去噪，没有这个累积问题。

### 补充路线（当视频模型不好用）

| 路线 | 适用 | 代价 |
|---|---|---|
| **首尾帧 keyframe** 插值 | 只需要"从 A 姿势到 B 姿势"的过渡 | 需要模型支持 keyframe（我们的 `video` 工具支持） |
| **ComfyUI + AnimateDiff**（本地） | 有 GPU、想完全可控 | 要装权重、调 controlnet，学习曲线陡 |
| **逐件生成 + 骨架驱动**（我们之前做的 rig） | 需要精确控制关节 | **前提是部件能分开** —— 实测 AI 画不出可拆的部件，这条路上游就断了 |
| **手工/程序动画**（我们做的 procedural） | 占位、道具、几何体 | 美术上限低 |

## 三、落地实现：`spritesheet` 工具

```jsonc
// 1) 先确认 ffmpeg 和视频信息
spritesheet(action="info", video="D:\\动画\\walk.mp4")

// 2) 一条龙：视频 → 抽帧 → 抠底 → 对齐 → 精灵表 + JSON
spritesheet(action="from-video", video="D:\\动画\\walk.mp4",
            count=8, columns=4, scale=2, name="walk", loop=true)

// 3) 已经有 PNG 帧：直接打包
spritesheet(action="from-frames", frames=["D:\\f1.png","D:\\f2.png"], fps=12)

// 4) 把骨架动画烘成精灵表
spritesheet(action="from-rig", rig_config={project:"demo", name:"soldier"}, animation="walk_td", count=8)
```

产物：`<输出目录>/<项目>/anim/<名字>/` 下是 `<名字>_sheet.png` + `<名字>.json`

### JSON 格式（引擎无关，谁都能吃）

```jsonc
{
  "version": 1, "name": "walk", "image": "walk_sheet.png",
  "imageSize": [1232, 352],
  "cell": { "x": 0, "y": 0, "w": 308, "h": 176 },
  "grid": { "columns": 4, "rows": 2, "count": 8 },
  "fps": 4, "frameDurationMs": 250, "loop": true, "scale": 2,
  "pivot": [0.5, 1],          // 每格内的锚点：默认底边中点（站立角色贴地）
  "frames": [ { "index":0, "col":0, "row":0, "x":0, "y":0, "w":308, "h":176 }, … ]
}
```

运行时：按 `frames[i]` 从 `image` 里取格，按顺序播，间隔 `frameDurationMs`。

## 四、几个**必须做对**的细节（都是踩过的）

### 1. ★ 所有帧必须用**同一个包围盒**（防抖动）

逐帧各自紧裁再居中，会让角色每帧位置微微不同 —— 播起来就是**抖动**。这是 AI 视频转精灵表最常见的翻车点。

正确做法：先算所有帧的 **union 包围盒**，再统一裁。测试里专门有一条：
"三帧色块从左往右移动，打包后三格里的色块中心必须递增" —— 如果各自居中，三个中心会一样（看起来原地踏步）。

### 2. 抠底必须**从边缘泛洪**，不能全图颜色匹配

全图匹配会把角色身上与背景同色的区域一起抠掉（白底上的白牙、黑底上的黑靴都会变成洞）。
从边缘泛洪只吃"和外面连在一起"的那一片，角色内部的同色区安全。测试里有一条专测这个。

另外：边缘颜色不统一时（渐变、实景背景）**要拒绝抠** —— 硬抠会挖出奇怪的洞，不如老实告诉用户需要分割模型。

### 3. 循环动画要丢掉与首帧重复的末帧

视频循环的最后一帧往往和第一帧几乎一样。不丢的话，播放器会在末尾多停一帧，看起来"卡一下"。

### 4. 帧率不要照搬视频原帧率

游戏 sprite 通常 **8~12 帧**就够。一段 3 秒 30fps 的视频有 90 帧，全抽出来只是让文件变大 10 倍，视觉上看不出区别。
所以 `count`（"我要 8 帧"）比 `fps` 更直观 —— 插件内部用 `count / duration` 换算。

### 5. ffmpeg 找不到要**明确报错 + 给安装指引**

JavaScript 里没有靠谱的 mp4 解码器，这一步必须靠 ffmpeg。
所以 `findFfmpeg` 的查找顺序是：参数 → 环境变量 → PATH → 常见位置 → **按层浅扫**（BFS）。
找不到时返回 `howToFix` 数组，而不是静默失败或抛一个看不懂的错误。

> 顺便说：这台机器上 ffmpeg 就躺在剪映和 ComfyUI 的目录里，用户根本不知道有。
> 所以浅扫值得做 —— 但**必须按层**（BFS），深度优先会一头扎进某个子树把配额烧光（实测没找到）。

## 五、和之前「拆件骨架」路线的关系

两条路都留着，适用场景不同：

| | 视频抽帧 | 拆件骨架（rig） |
|---|---|---|
| 连贯性 | ✅ 视频模型保证 | ✅ 程序保证（数学上必然连贯） |
| 美术上限 | ✅ 高（模型画的） | ❌ 取决于分件质量 |
| 能否改动作 | ❌ 只能重新生成 | ✅ 改关键帧即可 |
| 上游风险 | 视频模型要能生成横向动作 | **AI 画不出可拆的部件**（实测：拆不开） |
| 适合 | 主要角色、复杂动作 | 数量大、需要变体、动作要复用 |

**放弃的是"让 AI 直接画出可拆部件"这个假设**，不是放弃 rig 本身 —— rig 仍然适合程序生成的素材（几何道具、我们那套俯视士兵）。

## 七、实测记录：用你游戏里的士兵跑通的全流程

> 这一节全部是**真跑出来的数字**，不是理论。素材来自 `doomsday-ember` 的 `idle_soldier_1.png`。

### 流程

```
① 锚点：从素材表裁出一个单位 → 居中放到 608×352
② 图生视频（i2v，本地 MiniMax H3）：锁死机位 + 锁死外观
③ 抽帧
④ 边缘泛洪抠底
⑤ 共同包围盒对齐 → 精灵表 + JSON
```

### 实测数字

| 步骤 | 参数 | 结果 |
|---|---|---|
| 素材表 | 1248×832，4 个单位，平涂底 rgb(143,151,135) | 自动认出 4 个，裁第 1 个（184×332） |
| 锚点 | 608×352，fillRatio 0.92 | 缩放 0.98×，居中 |
| 走路视频 | 608×352 · 124 帧 @24fps · 5.17s | 本地约 2 分钟 |
| 抽帧 | count=50 → 9.67fps | 50 帧 |
| 自动循环 | 第 1 帧最像第 29 帧（差异 1.74） | 周期 28 帧 → 重采样成 **10 帧** |
| 抠底 | 容差 60 | 背景占 88.3%，全部抠掉 |
| 精灵表 | 10 帧 5×2 | **925×680**，每格 185×340 |
| 攻击视频 | 同上 | 8 帧 4×2 → 1360×652，含枪口闪光 + 后坐 |
| **八面图** | 环绕视频 → count=8 | **8 帧 1×8** → 1792×335，每格 224×335 |

### ★ 八面图不要用"画一张八方向表"

**试过，失败**：让图模型画"8 个均匀旋转视角的角色转身表"，它给 10 个角色但只有
**约 5 个不同朝向**（正视/背视/右侧反复出现），没有左侧、没有后 3/4。
这和图模型画"零件盘"是同一类失败：看起来像，但不按你的规格来。

**有效的做法：让视频模型绕角色转一圈，再等距抽 8 帧。**
视频是连续插值的，角度天然均匀；而且因为同一个 i2v 首帧，外观也统一。

```
spritesheet(action="anchor",  image="素材表.png", unit_index=0)        → 锚点图
   ↓  用锚点图做 i2v，提示词："camera orbits 360° around him, he stands still"
spritesheet(action="from-video", video="环绕.mp4", count=8, columns=8, loop=false)
```

### 循环接缝：用 `loop="auto"`

直接取前 N 帧播起来会**顿一下**（末帧接不回首帧）。`loop="auto"` 会：
先多抽一些帧（`count×5`，上限 60）→ 用 16×16 灰度指纹找"和首帧最像"的那一帧 →
把那一轮周期**重采样成你要的帧数**。

实测：走路那段的周期是 28 帧，重采样成 10 帧后循环是顺的。

### 为什么这套比"拆件骨架"实用

| | 视频抽帧（这套） | 拆件骨架（rig） |
|---|---|---|
| 连贯性 | 视频模型保证 | 程序保证 |
| 美术上限 | **高** | 取决于分件质量 |
| 八面图 | ✅ 一段环绕视频搞定 | 要 8 套分件 |
| 改动作 | 重新生成 | 改关键帧 |
| 上游风险 | 视频模型要能生成横向动作 | **AI 画不出可拆部件** |

### 注意（真实限制）

- **本地跑视频要显存**：RTX 5070 Laptop 8GB，`--lowvram` 下 608×352×124 帧约 2 分钟。显存不够就降尺寸或换云 API。
- **背景必须接近纯色**：i2v 会照着首帧的背景画。首帧是平涂底，视频就基本保持平涂；如果是实景背景，抠底会失败（工具会明确拒绝，不会硬抠）。
- **动作幅度受首帧限制**：i2v 更擅长"在原位动"（走路/开火/受击），不太会"跑出画面"。要位移就靠游戏代码移动贴图。
- **八面图的第 8 帧≈第 1 帧**：环绕一圈会回到原点，实际可用的不同朝向是 7~8 个，按需裁。

## 八、效率优化：别白干 80% 的活

流程跑通之后回头看，第一版有**三处明显的冗余**。都已经改掉。

### 1. ★ 两段式抽帧（最大的浪费）

**问题**：`loop="auto"` 要抽 `count×5` 帧（上限 60）才够找出周期，但最终只用 `count` 帧。
老做法是**全抽出来 → 全抠底 → 丢掉 80%**：要 10 帧，就白写 50 张全尺寸 PNG、
白抠 50 次（100 个文件躺在磁盘上）。

**改法**：
```
① 粗筛：count×5 帧，缩到 160px 宽 → 找周期（指纹本来就是 16×16，小图完全够）
② 精选：一次 ffmpeg select 调用，只把那 count 帧按**全尺寸**抽出来
③ 只抠这 count 帧
④ 粗筛目录用完即删
```

关键实现：ffmpeg 的 `select` 滤镜按帧号精确取帧（逗号要转义成 `\,`）：
```
-vf "fps=9.67,select='eq(n\,0)+eq(n\,3)+eq(n\,6)+...'" -vsync 0
```
精选必须用**和粗筛相同的 fps**，帧号才对得上时间轴。

**效果**：要 10 帧的话，磁盘写入从 100 个文件降到 10 个，抠底次数从 50 降到 10。

### 2. 结果缓存

同样的视频 + 同样的参数，第二次直接命中缓存。

**实测：692ms → 3ms（快 230 倍）。**

判重依据：视频的 **路径 + 字节数 + mtime**（内容变了 mtime 必变）+ 影响结果的参数
（count/fps/alpha/tolerance/columns/scale/loop/...）。`force=true` 强制重跑。

为什么值得做：用户常常只改 `scale` 或 `columns` 就重跑，而要出一次结果得走整条链路。

### 3. 周期比帧数短时**按周期封顶**（这是个真 bug）

想从 8 帧的周期里取 10 帧，重采样**必然出现重复帧** —— 实测：要 10 帧只抽出 8 个文件，
精灵表少两格。现在按周期封顶，并且明确告诉你"周期只有 8 帧，要 10 帧会出重复帧"。
想要更多帧就得**提高抽帧密度**（提高 count 的同时提高粗筛帧数），而不是硬凑。

### 4. 顺带：预览图开关（另一个吃磁盘大户）

`*_labeled.png` 曾经是**原尺寸**的 —— 1024×1024 素材的预览图也是完整 1MB PNG，
实测 535 张吃掉 **928MB**。现在默认缩到最长边 384px（体积约 2~3%），
也能设 `off` 完全关闭，或用 `purge_labeled` 清历史。详见 README「预览图开关」。

## 九、八面图的相位

**问题**：环绕视频转一圈会回到原点，所以直接取前 8 帧，第 8 帧≈第 1 帧，实际只有 7 个朝向。

**修法**：八面图要用 `loop="auto"` + `count=8`。

`auto` 会先识别出"转一圈"的周期，然后**在周期内**均匀取 8 个点（不含末尾那个和开头重复的点），
于是 8 帧是 8 个真正不同的角度。

```jsonc
spritesheet(action="from-video", video="orbit.mp4", count=8, loop="auto", columns=8)
```

**`phase` 参数**（0~1）：在周期里从哪个位置开始取。

| 场景 | 用法 |
|---|---|
| 八面图，想让第 1 帧严格对准正面 | `phase=0`（默认，看视频从哪开始） |
| 想让角色先看到侧面 | `phase=0.25` |
| 走路循环，想从"另一条腿迈出"开始播 | `phase=0.5` |

归一化的好处：和帧率、周期长度无关，换个视频不用改数字。

**实现上有个坑**：ffmpeg 的 `select` 只能按源顺序输出帧，而 phase 平移后会**跨过周期末尾回到开头**
（比如 20,21,…,7,8）。所以流程是：先按排序后的下标让 select 抽，再在内存里按 phase 的顺序重排
（`lib/spritesheet.js` 里 `sortedPicks` → `byIndex` 那一段）。顺序错了整套动作就是"倒着播/跳着播"，
而且只有肉眼才看得出来。

## 十、变体继承：同款换配色，不重跑管线

一个士兵做好后，"红/蓝阵营"、"缴获版"、"受损版"是常见需求。
如果每个变体都重走「锚点 → 图生视频 → 抽帧」，代价是：每变体几分钟生成 + **每变体细节都可能不一样**。

**变体继承只改颜色**，形状/动作/帧数/时序全部继承：秒级完成，且变体之间除配色外逐像素一致。

```jsonc
spritesheet(action="variant", sheet="soldier_walk_loop_sheet.png",
            variants=[{name:"soldier_walk_blue", preset:"blue"},
                      {name:"soldier_walk_red",  preset:"red"},
                      {name:"soldier_walk_damaged", preset:"damaged"}])
```

预设：`red / blue / green / purple / yellow / captured / damaged / ghost`

也可以手调：`hue`（色相旋转度数）、`saturation`、`brightness`、`grayscale`、`tint`、
`palette`（精确换色 `[[fromRGB,toRGB],...]`）。

**一个重要限制**：`hue` 是**全局**旋转，会把肤色、枪械金属色一起带走（实测蓝色变体里脸也变蓝了）。
只想换制服颜色就用 `palette` 精确指定颜色对。

产出的变体 JSON 会记下 `variant_of`（我是谁变的）和 `recolor`（用的什么配方），
以后要调色或重做能照着重复出来。

## 十一、动画装机：按**格子**缩放，不是按整图

静态图装机按"整图宽高"缩放。动画**不能这么干**：5×2 的表按整图缩放会得到 185.6 像素这种格子，
切帧必然错位。

`install(action="anim")` 的做法：
1. 按**格子**算倍率（`目标格宽 / 源格宽`），整表乘同一个倍率
2. 宽高倍率不一致就**拒绝**（强行拉伸会让角色变形），并给出建议的格子尺寸
3. 写到游戏目录的 `assets/anim/` 下（同名先备份 `.bak-before-install`）
4. 生成 `<名字>.anim.json`：运行时描述，帧坐标**按缩放后的实际值重算**（不能抄源 JSON）

```jsonc
install(action="anim-list", project="doomsday-ember-sprites")        // 看有哪些动画
install(action="anim", project="...", root="D:\游戏", cell_width=96, cell_height=176)  // 默认 dry_run
install(action="anim", project="...", root="D:\游戏", cell_width=96, cell_height=176, dry_run=false)
```

实测：185×340 的格子 → 目标 96×176，倍率 0.519，表变 480×353，10 帧坐标全部重算正确。

## 十二、产出目录收敛：哪张图是给游戏用的

插件一路加了太多副产物，平铺在一起根本分不清。现在按**四类**分：

| 类别 | 包含 | 去处 | 游戏引用它吗 |
|---|---|---|---|
| **source** | 干净素材、精灵表 | 原地不动 | ✅ **只有这类该被引用** |
| preview | `*_labeled.png`（印着名字） | `_preview/` | ❌ |
| derived | `*.post.png`、`*.pixel.png`、`*_slices/`、`*_{w}x{h}.png`、`*.alpha.png` | `_derived/` | 可能（切片可能是游戏在用的单张） |
| intermediate | `frames/`、`*.cache.json`、`*.bak*` | `_tmp/` | ❌ 删了能重跑 |

```jsonc
assets(action="layout",   project="xxx")   // 清点：各分类多少、游戏可用几个、可清理多少 MB
assets(action="organize", project="xxx")   // 演练（默认 dry_run）
assets(action="organize", project="xxx", dry_run=false)   // 真整理
```

**整理只动 preview + intermediate，绝不动 source**（它被代码引用着，移动等于断引用）。
`derived` 默认也不动 —— `*_slices/` 这种目录很可能就是游戏在用的切片。要动必须
`include_derived=true`，那时会给出警告。

## 十三、效率与冗余：这一轮的账

### 1. 抠底改并发（纯 CPU 活不该串行）

抠底是 PNG 解码 + 逐像素泛洪 + 编码，全是 CPU。原来逐帧串行，50 帧要好几秒。
现在 `mapLimit` 限并发：

| 阶段 | 并发 | 理由 |
|---|---|---|
| 粗筛帧抠底 | 6 路 | 帧只有 160px，小图并发安全 |
| 精抽帧抠底 | 4 路 | 全尺寸帧内存占用大，4 路是吞吐拐点（再高被内存带宽拖住） |

### 2. 变体去重（同配方不重算）

变体做完会把**配方 + 源图 mtime/size** 记进 JSON。下次同配方直接命中：

```
第 1 次 153ms → 第 2 次 24ms（命中）
改配方 → 重做；force=true → 重做
```

判据里带 mtime 很关键：源图重画过 mtime 必然变，那时必须重做 —— 只看文件名会拿到过期变体。

### 3. 磁盘守卫（把教训变成代码）

写盘前先看空间：`ok` 放行 / `low` 先自动清理再复查 / `critical` 拒绝并给出修复步骤。
清理**只删可再生文件**（预览图、中间产物、缓存）。

这条的重点不是"清理"，而是**提前判断**：那次事故真正的问题是"写到一半 ENOSPC，
报错看不出是磁盘满了"。

### 4. 实测账（本机，输出目录 907MB）

| 分类 | 数量 | 大小 | 处理 |
|---|---|---|---|
| source（游戏用） | 2255 | 759.8 MB | **不动** |
| derived（切片/后处理） | 1280 | 144.6 MB | **默认不动**（`_slices/` 可能是游戏在用的单张） |
| intermediate（`frames/` 等） | 18 | 1.3 MB | ✅ 已清 |
| config（JSON） | 542 | 1.4 MB | 不动 |

清理后磁盘 130.1 GB 可用（这次没被塞满，是因为上一轮已经清掉 928MB 的预览图 + 改了默认策略）。
